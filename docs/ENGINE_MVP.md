# Архитектура Calculation Engine (MVP и V2)

Этот документ описывает текущее состояние (Q1 2026) подсистемы расчётов, включая параллельную работу двух движков (Dual Calculator), политику обработки неизвестных данных и механизмы миграции на V2.

---

## 1. Два движка: Legacy vs V2

В системе сосуществуют две реализации расчётного ядра. Это сделано для безопасной миграции без риска сломать существующую логику (Legacy), постепенно внедряя новую архитектуру (V2).

### Legacy Engine
- **Текущий Production-стандарт.**
- Монолитная логика, жестко закодированные правила (hardcoded if/else).
- Сложно расширять, трудно тестировать граничные случаи.
- **Всегда является источником правды** в режиме `dual`.

### V2 Engine
- **Новая модульная архитектура.**
- Основана на **Правилах (Rule-based)**: логика вынесена в базу данных (`calc_incoterms_rules`, `calc_insurance_rules`).
- Изолированный пайплайн: `Normalization -> Selection -> Execution -> Assembly`.
- Поддерживает **Tri-state логику** (yes/no/unknown) для включений расходов.

### Legacy vs V2 — принципиальное отличие

|                        | Legacy	                | V2	                |
| ---------------------- | ----------------------- | ------------------- |
| Неизвестные данные	   | Молча «догадывается»	   | Явно фиксирует	   |
| Расхождения	           | Невидимы	               | Видны в diff	       |
| Расширяемость            | Низкая	               | Высокая	           |
| Контроль	           | Через код	               | Через правила	       |

Legacy сохранён:
- как fallback,
- как точка сравнения,
- для снижения рисков.

## 2. Режимы работы (CALC_ENGINE)

Режим управляется переменной окружения `CALC_ENGINE`.

| Режим | Поведение | Описание |
| :--- | :--- | :--- |
| **`legacy`** | Только Legacy | Классический режим. V2 не запускается. Используется при критических багах V2. |
| **`v2`** | Только V2 | **Целевой режим.** Работает только новый движок. |
| **`dual`** | **Dual Run** (Default*) | Запускает **оба** движка параллельно. Возвращает результат Legacy, но логирует сравнение с V2 в `calculation_trace`. |

> *Примечание: В коде дефолт `v2` (из `config.ts`), но логика оркестратора может откатываться на `legacy` при невалидном значении.*

### Переключение
В `.env`:
```bash
CALC_ENGINE=dual
# или
CALC_ENGINE=v2
```

### Флаг `V2_CUSTOMS_VALUE_IMPL`
Управляет конкретно логикой расчета таможенной стоимости внутри пайплайна.
- `v2`: Использует класс `CustomsValueCalculatorV2` (новая логика с правилами).
- `legacy`: Даже внутри V2 пайплайна вызывает старый `CustomsValueCalculator`.
Позволяет тестировать обвязку V2 (нормализация, сборка), но со старой математикой.

## 3. Изолированный V2 Pipeline

Архитектура V2 строго разделена на фазы:

1. **Normalization (Нормализация)**
   - Приведение входных данных к строгому формату.
   - Пример: `country_of_origin` → если нет, ставится дефолт `'CN'` (Китай).
   - **Tri-state Normalization**: Булевы поля (включает ли инвойс фрахт/страховку) преобразуются в `'yes' | 'no' | 'unknown'`.
     - Используются поля: `v2_freight_inclusion`, `v2_insurance_inclusion`.
     - Это важно, чтобы отличать "пользователь сказал НЕТ" от "пользователь ничего не сказал".

2. **Rule Selection (Выбор правил)**
   - Загрузка конфигурации из БД (`RuleRepository`).
   - `IncotermsRule`: Что входит в инвойс, какие компоненты критичны.
   - `InsuranceRule`: Ставки страхования (глобальные или по странам).
   - Сейчас правила в основном Read-only.

3. **Execution (Выполнение)**
   - Расчет логистики (Legacy компонент переиспользуется).
   - Расчет таможенной стоимости (`CustomsValueCalculatorV2`).
   - Расчет пошлин и НДС (`DutyVatCalculator`).

4. **Assembly (Сборка)**
   - Агрегация всех источников, допущений (assumptions) и ошибок.
   - Формирование итогового `CalculationPackage`.

## 4. Политики обработки Unknown (Tri-state)

В Legacy отсутствие галочки означало "Нет". В V2 мы различаем `unknown`.
Политика определяется правилом инкотермса (`unknown_policy`).

### Policies
1. **ESCALATE**: Если значение неизвестно — **ошибка/требование эскалации**.
   - Пример: `DDP` (пока всегда требует ручного разбора).
   - Пример: `DAP` (часто требует уточнения).
   
2. **ASSUME_DEFAULT** (Компромисс MVP): Если значение неизвестно — **предполагаем дефолт**.
   - Используется для массовых условий (CIF, FOB).
   - Индустриальный стандарт:
     - **CIF/CIP**: Предполагаем, что фрахт и страховка **включены** (`yes`), если явно не сказано обратное.
     - **FOB/EXW**: Предполагаем, что **НЕ включены** (`no`).
   - В трейс пишется Assumption: `ASSUMPTION_INSURANCE_INCLUSION`.

## 5. Таймауты и Отказоустойчивость

### Dual Mode
- **Legacy**: Ждет завершения.
- **V2**: Жесткий таймаут **1.5 сек**.
- Если V2 не успел:
  - Возвращается результат Legacy.
  - В `trace` пишется `v2_timeout: true`.
  - Ошибки V2 **не ломают** ответ пользователю (try-catch вокруг сравнения).

### V2 Mode
- **Мягкий таймаут 5 сек**.
- Если V2 не успел:
  - **НЕ возвращает 500**.
  - Возвращает статус `incomplete`.
  - Reason code: `V2_TIMEOUT`.
  - Это позволяет фронтенду показать частичные данные или просьбу повторить, вместо падения.

## 6. Calculation Trace и Отладка

В режиме `dual` результат содержит блок `calculation_trace.engine_comparison`:

```json
"engine_comparison": {
  "mode": "dual",
  "v2_status": "ok",
  "v2_confidence": "high",
  "diff_summary": {
    "diff_count": 1,
    "diffs": [
      {
        "path": "customs_value_usd",
        "legacy": [100.0, 100.0],
        "v2": [100.5, 100.5]
      }
    ]
  }
}
```

### Как дебажить расхождения (Golden Runner)
1. Запустить тесты/расчет в режиме `dual`.
2. Смотреть логи или JSON ответа. Раздел `diff_summary` покажет, где математика разошлась.
3. Расхождения допускаются в пределах:
   - $0.01 для сумм (customs value, landed cost).
   - 1e-9 для ставок (VAT rate).
   - Разные наборы Reason Codes считаются расхождением.

### Stop Conditions (Чего быть не должно)
- **VAT Rate Mismatch**: Ставка НДС должна совпадать идеально.
- **Incoterms Mismatch**: Интерпретация условий поставки должна быть одинаковой.

## 7. Известные ограничения MVP

1. **DDP всегда requires escalation**: Автоматический расчет DDP сложен, пока всегда отправляется к менеджеру.
2. **Duty/VAT partially legacy**: Калькулятор пошлин частично использует старую логику, даже в V2 пайплайне.
3. **Read-only Rules**: Правила загружаются из БД, но система не умеет их динамически обновлять/обучать на лету.
4. **V2 Customs Flag**: Полная сила V2 (с правилами) работает только если `V2_CUSTOMS_VALUE_IMPL='v2'`.

## 8. Что осталось до Production

1. Полный перенос Duty/VAT на конфигурацию из правил (отказ от хардкода ставок), как с ними определимся.
2. Загрузка правил из БД (сейчас `RuleRepository` частично замокан и использует фиксированные версии).
3. Стабилизация и расширение справочников тарифов и Инкотермс для всех стран.
4. Расширение механизма `ASSUME_DEFAULT` на более сложные кейсы.
5. Валидация правил с доменными экспертами (таможня / торговля).


### Итог

На текущем этапе система стабильно считает, не врёт молча, объясняет свои решения, готова к развитию без переписывания ядра.
