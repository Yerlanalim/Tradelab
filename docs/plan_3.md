## Анализ текущего состояния (по коду и документам)

### Что сейчас сделано в этом чате/коде (фактическая реализация)
- Поиск поставщиков P3 работает через Edge Function `chat_handler` и OpenAI Responses API.
- Модель для всех запросов, включая web search: `gpt-4o-mini` (см. `basePayload.model`).
- В `buildSearchPrompt()` жёстко ограничены источники: только Alibaba и Made‑in‑China.
- Вызов веб‑поиска выполнен через `tools: [{ type: "web_search" }]` + `tool_choice`.
- Ответ ожидается как **чистый JSON** формата `SupplierSearchResult`.
- Есть пост‑фильтры качества:
  - проверка домена и URL-паттернов (только карточки товара);
  - отбрасывание плейсхолдеров типа “Supplier 1”;
  - дедуп по нормализованному имени компании;
  - приоритизация Alibaba/MIC и fallback‑поиск по каждой площадке.

### Почему результаты хуже, чем в ChatGPT
1) **Слабее модель.** `gpt-4o-mini` заметно уступает качеству web‑search и извлечению фактов.
2) **Мало сигналов для поиска.** В промпте нет явных search‑query шаблонов (например `site:alibaba.com reach stacker 45t`), нет требования собирать реальные доказательства по карточке.
3) **Нет реальной валидации ссылок.** Проверка основана на regex‑паттернах URL, но не на фактической загрузке страницы.
4) **Не используются сырые данные веб‑поиска.** Код берёт только текст ответа модели, не извлекая исходные ссылки/цитаты из web_search.
5) **Слишком жёсткий формат.** Модель обязана вернуть чистый JSON, что провоцирует галлюцинации и «придуманные» ссылки.

### Пример ожидаемого качества (PDF по ричстакерам)
В отчёте из примера есть:
- реальные карточки, цены и диапазоны;
- статусы поставщиков (Diamond/Audited, стаж);
- дополнительные параметры модели и контекст.
Сейчас схема `SupplierSearchResult` не просит эти поля, поэтому модель их не собирает.

## Основные проблемы качества данных

1) **Ссылки не всегда реальные и не проверены**
- Проблема: ссылки валидируются только по домену и path‑паттернам.
- Почему критично: пользователь получает «псевдо‑карточки» и теряет доверие.
- Что нужно: HTTP‑валидация страницы + проверка типа (product page vs search/news/blog).

2) **Низкая полнота и релевантность**
- Проблема: `gpt-4o-mini` + строгий JSON → модель урезает детали и “заполняет пробелы”.
- Почему критично: неполные или некорректные карточки.
- Что нужно: перейти на более сильную модель для этапа поиска/извлечения.

3) **Нет извлечения ключевых атрибутов из карточек**
- Проблема: схема items слишком бедная (нет model/brand/status/years/verification).
- Почему критично: отчёт хуже реального поиска и хуже ChatGPT.
- Что нужно: расширить схему под реальные поля (модель, статус, стаж, тип компании).

4) **Нет мультишаговой стратегии поиска**
- Проблема: один pass поиска с ожиданием, что модель соберёт всё сама.
- Почему критично: web‑search хуже структурированного пайплайна “поиск → сбор URL → парсинг”.
- Что нужно: ввести pipeline из 2–3 шагов.

5) **Дедуп может съедать релевантные варианты**
- Проблема: дедуп по нормализованному названию убирает вариации бренда/дилера.
- Что нужно: дедуп по комбинации (name + link domain + модель), а не только по имени.

## Что нужно исправить (детально)

### 1) Модель и режим поиска
- **Исправить:** заменить `gpt-4o-mini` на более сильную модель для web‑search этапов.
- **Почему:** качество ссылок и извлечения фактов выше.
- **Кандидаты:** `gpt-4o`, `gpt-4.1`, `gpt-5` (если доступен).

### 2) Запросы к web_search должны быть управляемыми
- **Исправить:** формировать системный search‑query шаблон.
- **Почему:** web_search должен искать именно продуктовые карточки.
- **Пример:** `site:alibaba.com "reach stacker 45 ton" "product-detail"` + отдельный запрос для MIC.

### 3) Многошаговая стратегия (search → verify → extract)
- **Шаг A:** собрать 15–30 URL на Alibaba/MIC через search API.
- **Шаг B:** проверить каждый URL (HTTP 200, тип страницы).
- **Шаг C:** извлечь поля с помощью модели или лёгкого парсинга HTML.
- **Почему:** так повышается точность и реальность ссылок.

### 4) Расширить схему результата
- **Добавить поля:** `model`, `supplier_type`, `years_on_platform`, `verification_badges`, `product_type`.
- **Почему:** сравнимая ценность с ChatGPT/ручным поиском.

### 5) Валидация и нормализация ссылок
- **Исправить:** подтверждать ссылку через HEAD/GET и проверку мета‑сигнатур (title/og:type).
- **Почему:** сейчас паттерны URL дают ложные срабатывания.

### 6) Источники и резервные пути
- **Исправить:** при нехватке результатов использовать дополнительные источники или другой поисковик.
- **Почему:** текущий fallback всё равно упирается в тот же web_search.

## Оценка вариантов улучшения

### Вариант A — Переход на сильную модель (GPT‑5/4.1/4o)
**Плюсы:**
- Резкий рост качества и точности ссылок.
- Больше фактических деталей, меньше галлюцинаций.
**Минусы:**
- Дороже по cost/token.
**Рекомендация:** да, но только в связке с проверкой ссылок.

### Вариант B — Baidu Search API как источник
**Плюсы:**
- Более стабильный веб‑поиск (особенно для китайских источников).
- Можно получать URL‑кандидаты отдельно от LLM.
**Минусы:**
- Нужно развернуть pipeline парсинга и нормализации.
**Рекомендация:** хороший вариант для этапа “сбор URL”.

### Вариант C — Гибрид (лучший путь)
1) Baidu/другой search API → собираем URL.
2) Быстрый валидатор страниц.
3) LLM‑extractor (модель сильнее, но в меньшем объёме).
4) Скоринг/дедуп и финальная сборка.
**Плюсы:** максимальное качество и контроль.
**Минусы:** больше инженерии.

## Что доделать при новом старте (приоритет)
1) **Сменить модель** для поискового этапа.
2) **Разделить поиск на pipeline** и ввести проверку URL.
3) **Расширить схему items** с полями из реальных карточек.
4) **Использовать отдельный search‑API** (Baidu/Bing/SerpAPI) для сбора URL.
5) **Добавить метрики качества**: % валидных ссылок, % Alibaba/MIC, % пустых полей.
