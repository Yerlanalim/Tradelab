# Plan 2 — Что осталось до запуска TradeLab (январь 2026)

Документ: пошаговый план доведения проекта до запуска, на базе текущего кода (Next.js + Supabase + Edge Functions) и концепции v2.2 + **единого бота с режимами** (см. `docs/TradeLab_Unified_Bot_Concept_v1.md`).

## 0) Что считаем «запуском» (обновлено)

**Запуск = готовая к продаже линейка P1+P2+P3+P4 + единый UX отчётов (web/PDF/экспорт) + единый AI‑бот (с режимами) + контентные разделы + лендинг + дисклеймеры + Trade Credits (баланс + списание).**

Ключевое правило: **монетизацию включаем через Trade Credits (TC)**: платные действия списывают TC; пополнение TC делаем через **Halyk ePay**.  
Важно: **legacy scrapers не используем и удаляем из платформы** (качество хуже, чем поиск через бота).

## 2) Пошаговый план до запуска (обновлённые приоритеты)

Принцип: сначала делаем **единый бот (unified bot) как “пульт управления” платформой** и только затем “добиваем” UX/форматы отчётов.  
**Trade Credits вводим рано**, чтобы P3 можно было продавать и тестировать конверсию; пополнение TC — через **Halyk ePay**.  
QCC/Tendata подключаем после получения доступов, не ломая UX.

### Milestone 0 — Unified Bot “фундамент”: режимы + единая Edge Function + UI‑контракт
**Цель:** один бот на платформе, который работает в режимах **Assistant / Supplier Search / Report** и управляет UX через `ui_hints`.

#### 0.0 Legacy cleanup (обязательно, до/параллельно Milestone 0)
**Цель:** убрать старые контуры так, чтобы не мешали unified‑подходу и не создавали “двойную правду” в коде/доках/Supabase.

- [ ] **Legacy scrapers (полное удаление)**
  - Supabase: снять/удалить Edge Function `apify_proxy`, убрать `APIFY_TOKEN` и любые env‑переменные legacy scrapers.
  - Frontend: удалить/заменить `Product3Search` и клиентский wrapper `searchSuppliers`, которые дергают `apify_proxy`.
  - UX: на `/products/supplier-search` больше нет “legacy поиска” — только Supplier Search mode (LLM web search).
  - Данные: определить политику по `supplier_*` (оставляем как feature store для канонизации/кеша, но источник legacy больше не пишем).

- [ ] **AI‑контур legacy**
  - `ai_orchestrator` остаётся временно, но считается **legacy**: новый “единый бот” ходит через `chat_handler`.
  - Определить cutover: после запуска `chat_handler` перевести фронт на новый endpoint и отключить использование `ai_orchestrator`.

- [ ] **Платежи legacy**
  - В домене `payments` используем только provider=`halyk` (Halyk ePay).
  - Убрать из доков/конфига любые упоминания Stripe/Kaspi (не используем).

#### 0.1 Edge Function `chat_handler` (единая точка входа)
- [ ] Принимает `messages`, `page_context`, `session_id` (+ user/session token).
- [ ] Определяет `mode` по `page_context`.
- [ ] Возвращает: `response`, `tool_calls` (если разрешены), `suggested_chips`, `ui_hints` (например, “redirect_to”).
- [ ] Серверно запрещает “опасные” tool calls вне нужного режима (anti‑bypass).

#### 0.2 Хранилище чата и состояния flow
- [ ] `chat_history` хранит не только `section`, но и **`mode`** и **`flow_state`** (для Supplier Search).
- [ ] Миграция/совместимость с текущими записями `chat_history`.

#### 0.3 UI (единый чат)
- [ ] В сайдбаре всегда один чат.
- [ ] В режиме Assistant при запросе “найти поставщиков” — чип/ссылка и редирект на `/products/supplier-search` (не запуск поиска).
- [ ] В режиме Supplier Search — special UI (preview/paywall/progress).

### Milestone 1 — Product 3 (Supplier Search mode): flow + качество + стабильность
**Цель:** P3 работает как платный guided flow на странице `/products/supplier-search`.

#### 1.1 UX‑контур (обязательный)
- [ ] **Диалог вместо формы как главный UX**
  - Вход: “опиши что ищешь” → бот уточняет (2 цикла максимум).
  - Бесплатный **preview** (3–5 примеров), чтобы подтвердить направление поиска.
  - Платный запуск “полного анализа” (после внедрения Trade Credits).
- [ ] **Интерактивный отчёт**
  - Сводка + бенчмарки (price/MOQ) + top‑10 поставщиков.
  - Светофор 🟢🟡🔴 и объяснимые факторы (evidence-first), без “гарантий”.

#### 1.2 Технический контур (обязательный)
- [ ] **Серверная сборка результата**
  - Результат хранится в `reports.result_summary` как структурированный JSON (устойчивый к рендерам/экспортам).
  - Логирование `api_usage(provider='openai')` с метаданными (время, токены, итоговый размер выдачи).
- [ ] **Стабильность**
  - Таймауты, ретраи, деградация ответа (“не уверен — уточняю”) вместо галлюцинаций.
  - Понятные ошибки пользователю (без технических деталей).

#### 1.3 DoD
- [ ] Пользователь получает “топ‑10” за 2–3 минуты.
- [ ] Пользователь понимает: “какой ценовой коридор”, “почему эти поставщики”, “что делать дальше”.

### Milestone 2 — Trade Credits (TC) Core: ledger + баланс + бонусы/expiry (MVP)
**Цель:** платные действия на платформе работают через внутренние Trade Credits.

#### 2.1 Модель данных TC (адаптация под наш Supabase)
- [ ] **Ledger-first**: отдельная таблица транзакций TC как источник истины (начисления/списания/возвраты/сгорания).
- [ ] **Expiry** для бонусов/промо: хранение “пакетов” с `expires_at`, чтобы списывать “с ближайшим истечением” (Promo → Bonus → Purchased).
- [ ] **Типы TC**:
  - Purchased (бессрочно)
  - Bonus (срок, например 6 месяцев)
  - Promo/Seasonal (короткий срок, например 30 дней)
  - Welcome (короткий срок, например 3 месяца)

#### 2.2 Правила списания и возвратов
- [ ] **Идемпотентность списания**: один платный запуск = одно списание (защита от повторных кликов/ретраев).
- [ ] **Refund**: если “полный анализ” не дал результат/упал — автоматический возврат TC (или не списывать до “start”, но тогда нужен резерв/hold).

#### 2.3 Продуктовые бонусы (учесть сразу)
- [ ] **Реферальные бонусы** (регистрация друга, первая покупка).
- [ ] **Сезонные кампании / промо** (ограниченные по времени).
- [ ] **Награды за действия** (beta, отзыв, первые отчёты) — с прозрачными правилами и сроками.

#### 2.4 UI (минимум)
- [ ] Баланс TC (хедер) + страница “Trade Credits” (баланс по типам + истечения + история).
- [ ] Унифицированный модал подтверждения списания перед платным действием.

### Milestone 3 — Пополнение Trade Credits через Halyk ePay (Halyk‑only)
**Цель:** пользователь покупает пакеты TC через Halyk ePay, TC начисляются автоматически.

- [ ] **Пакеты TC** (Starter/Pro/Business/Enterprise) + бонусы пакета (Bonus TC с expiry).
- [ ] **Интеграция Halyk ePay**
  - Создание платежа, редирект/виджет, получение подтверждения.
  - Webhook/серверное подтверждение статуса, идемпотентность по `provider_ref`.
- [ ] **Связь с нашим доменом `payments`**
  - Используем `payments` для покупок пакетов TC (provider = `halyk`).
  - Убираем Stripe/Kaspi из планов/флоу (не используем).

### Milestone 4 — Довести контентные разделы (1–4 дня)
**Цель:** “скелет” контента готов, наполнение можно добавлять постепенно.

- [ ] **Карта**
  - Доточить визуальную часть (позиционирование/подписи/читаемость).
- [ ] **Выставки**
  - Добавить список выставок в раздел “Выставки” + связать со ссылками с карты (минимум навигация/фильтрация).
- [ ] **Библиотека**
  - Сделать удобный каркас: категории/теги/поиск/карточки. Контент наполняем итеративно.

### Milestone 5 — Нормализовать работу единого бота (2–5 дней)
**Цель:** единый бот полезен, предсказуем, evidence-first, и не путает режимы.

- [ ] **Единые правила ответов**
  - Структура ответа, блоки “Источник/Ограничение”, отсутствие “гарантий”.
- [ ] **Режимы и routing**

- [ ] **Ретраи/ошибки**
  - Ошибка OpenAI/edge не ломает UX: нормальные сообщения, логирование, деградация.

### Milestone 6 — Нормальный лендинг (2–6 дней)
**Цель:** объяснить ценность, продукты, кейсы, дисклеймеры и привести к регистрации.

- [ ] **Структура лендинга**

- [ ] **SEO/мета**
  - Title/description/OG, базовые ключевые страницы.
- [ ] **Доверие**
  - “Как мы получаем данные”, “что мы НЕ гарантируем”, политика конфиденциальности.

### Milestone 7 — Формы и форматы отчётов “на 100% готовы” до подключения API (3–10 дней)
**Цель:** к моменту получения API от QCC/Tendata остаётся только “подключить данные”, без переделки UX/экспорта/PDF.

- [ ] **Унифицировать content model отчётов P1–P4**
  - Что хранится в `result_summary` (web), что попадает в PDF, что в экспорт (CSV/XLSX).
- [ ] **Готовые шаблоны PDF для P1/P2/P4**
  - Структуры страниц, блок “evidence-first”, место под графики/таблицы.
- [ ] **Экспорт (Excel/CSV)**
  - Для каждого продукта определить табличную модель и подготовить реализацию экспорта (даже если данные пока демо).
- [ ] **Статусы/ошибки**
  - `draft/processing/ready/failed` отображаются одинаково во всех продуктах.

### Milestone 8 — Подключение QCC + Tendata (после получения API) (1–3 недели)
**Цель:** заменить демо‑данные реальными, не ломая UX.

- [ ] **QCC (P1)**
  - Реализовать/задеплоить `qcc_proxy` под **QCC Lite API** (как в v2.2) + нормализация + лог `api_usage(provider='qcc')`.
  - Учесть гибрид: часть данных официальная (QCC), часть — AI web search (в режиме Report).
- [ ] **Tendata (P2 + P4)**
  - Реализовать/задеплоить `tendata_proxy`, токен (2 часа), кеш, backoff на 429, лог `api_usage(provider='tendata')`.
- [ ] **Сшивка Supplier ID / feature store**
  - Bot‑поиск→каноник (через ссылки/названия + подтверждение пользователя), Tendata/QCC→каноник, хранение агрегатов/признаков.

### Milestone 9 — Операционка TC: мониторинг, алерты, возвраты, поддержка (3–10 дней)
**Цель:** минимизировать деньги‑риски и “споры” вокруг списаний/начислений.

- [ ] Реконсиляция: сверка `payments` ↔ начисления TC ↔ ledger.
- [ ] Политика возвратов для покупок TC (Purchased) и ограничений для бонусов (Bonus/Promo).
- [ ] Поддержка: шаблоны ответов, SLA, логирование спорных кейсов.

## 3) Дисклеймеры (обязательно сделать до запуска)

**Цель:** юридическая чистота и корректные ожидания пользователя.

- [ ] **Глобальные дисклеймеры**
  - AI может ошибаться, данные могут быть неполными/с задержкой, результаты носят инфо‑характер.
- [ ] **Дисклеймеры по продуктам P1–P4**
  - P1: не юридическое заключение.
  - P2/P4: таможенные данные с задержкой, объёмы оценочные.
  - P3: бот формирует shortlist и риск‑индикаторы как triage; требуется проверка по P1/P2; возможны ошибки/неполнота.
  - Trade Credits: купленные TC — не истекают; бонусные/промо — истекают; правила списания/возвратов описаны на странице TC.
- [ ] **Размещение**
  - UI (в отчётах и в продуктах), PDF, лендинг, Terms/Privacy.

## 4) Критические риски перед запуском и как их закрыть

- **Ожидания от AI/данных**: пользователи воспринимают как гарантию.
  - Митигация: короткие дисклеймеры в UI + evidence-first блоки + “что проверять дальше”.
- **Путаница режимов единого бота**: пользователь не понимает, почему “поиск” не запускается из Assistant.
  - Митигация: чёткие визуальные различия режимов, явные чипы/CTA, объяснение “полный поиск доступен в разделе Поиск поставщиков”.
- **Обход ограничений режима**: попытка выполнить “полный поиск” вне Supplier Search.
  - Митигация: серверная проверка `mode` в `chat_handler` и запрет tool calls вне режима.
- **Качество bot‑поиска / галлюцинации**: неверные/непроверяемые ссылки и факты.
  - Митигация: preview перед оплатой, строгий JSON‑формат ответа, human‑in‑the‑loop, “не уверен → уточняю”, явные ограничения/источники.
- **Риски Trade Credits**: спорные списания/начисления, повторные списания, истечение бонусов.
  - Митигация: ledger‑модель, идемпотентность, авто‑refund при сбоях, прозрачная история, напоминания об истечении.
- **Юридическая чистота данных** (Tendata/QCC).
  - Митигация: хранить агрегаты/признаки, не хранить сырые построчные записи; проверить ToS поставщиков данных.
